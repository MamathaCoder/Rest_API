JWT tokens

After login, the server hands you a JSON Web Token. It has three parts joined by dots: header, payload and signature. Anyone can read the payload, but only the server can sign it, so changing it breaks the signature.





The signature here uses a toy hash for the demo. Real servers use HMAC or RSA. Never put passwords in a JWT: the payload is readable.

    Caching with ETag
    

    The server tags each version of a resource with an ETag. Next time you ask, send it back with If-None-Match. If nothing changed, you get a tiny 304 instead of the whole body.
    

    

    No requests yet.
    

    Cache-Control: max-age=60 goes further: the client skips the request entirely for 60 seconds.
    

    


    

    CORS
    

    Browsers block a page from reading responses from a different origin unless that server allows it. Set up a scenario and see the outcome. Note: CORS is enforced by the browser, not the server.

    Idempotency keys
    

    A network drops the response to a payment. Did it go through? The client retries, and a naive server charges twice. An Idempotency-Key lets the server recognize the repeat.
    

    

    

    No payments yet.
    Charged: ₹0
    

    GET, PUT and DELETE are naturally idempotent. POST is not, so payment APIs like Stripe use keys.
    

    


    

    Webhooks vs polling
    

    Polling means asking “is it done yet?” again and again. A webhook flips it: the server calls your URL when something happens. A payment completes at second 6.
